  the most quotable sentence available.

## D. Which two defects to explain deeply

Seven pages cannot carry five case studies. **Recommended: DEF-003 and DEF-001 deep; DEF-002,
DEF-004, DEF-005 in a compact table.**

This differs from the expected pick of DEF-002, deliberately. DEF-002 and DEF-003 teach the *same*
lesson — an oracle written from the implementation instead of the specification — and two of seven
pages should not both make one point. DEF-003 is the stronger instance of it:

- DEF-002's bad assertion checked that a note appeared in `reasons`. Cosmetic consequence.
- DEF-003's bad assertion required a raw `NullPointerException` — behaviour FR-08 explicitly
  forbids — inside **`InputValidationTest`, the class whose entire purpose is FR-08 compliance**,
  under the `@DisplayName` *"a null payment or order is rejected at construction"*. A test class
  named after a requirement, certifying in plain English the thing that requirement prohibits.

Mention DEF-002 in one sentence within the DEF-003 discussion, as the first appearance of the
pattern. It corroborates without costing space.

**DEF-001 is the second deep dive** because it teaches a different lesson and anchors §6, which is
separately graded: a method every decision-table case exercised, with the semantic partition still
untested. Oracle independence and coverage limits are two distinct ideas.
